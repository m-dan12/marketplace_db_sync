# План: база данных как фундамент для ML-подсортировки

Статус: план утверждён владельцем; этапы 1–2 реализованы (см. раздел 11).
Аналитик в ближайшие месяцы недоступен, поэтому открытые вопросы из раздела 8
решаются по данным и помечены как допущения.

## 1. Цель

Задачи, на которые в итоге должна отвечать система:

1. **Что шить / не шить** — по каждому артикулу (модель + вариант + размер).
2. **Куда везти готовое** — одно из четырёх направлений: `ВБ`, `Озон`,
   `Склад`, `Склад Квант`.

Этот этап **не обучает боевые модели**. Задача этапа — чтобы каждый день
копились чистые, воспроизводимые данные, и чтобы к моменту, когда данных
хватит, можно было сразу сравнить модель с базовой формулой аналитика.

Решения по-прежнему принимает аналитик. Система только даёт рекомендацию
и записывает, что предложила и что было решено.

## 2. Принципы

- **Проект `marketplace_db_sync` расширяем, не заменяем.** Архитектура та же
  (domain / application / infrastructure / interface), порты и фейки для тестов.
- **Ничего не перезаписывается без следа.** Остатки, цены, статусы заданий —
  снэпшотами или журналом изменений. Иначе потеряем историю, на которой
  придётся обучаться.
- **Идемпотентность.** Любой сбор можно перезапустить за тот же день, дублей не будет.
- **Таблицы Google — только чтение** (сервисный аккаунт). Мы ничего в них не пишем.
- **Сырое хранится отдельно от расчётного.** Сначала данные как пришли, потом
  справочники и признаки. Правила разбора можно будет менять без повторного сбора.
- **Даты, а не номера недель.** В таблицах нумерация недель менялась
  («новая нумерация с 32 недели»), поэтому ключ всегда календарная дата.
- **Секреты не копируем в репозиторий.** Ключ сервисного аккаунта берётся из
  переменной окружения с путём к файлу и остаётся в `.gitignore`.

## 4. Модель данных

Схема расширяет существующий `schema.sql`. Названия рабочие.

### 4.1 Справочники (dim)

- `dim_article` — артикул целиком (`PT5930/6-17-17/1`) и его разбор: модель
  (`PT5930`), вариант/размер, бренд, категория, номер ткани, м/изд, квант кратности.
  Правило разбора артикула нужно согласовать с аналитиком (раздел 8).
- `dim_fabric` — номер ткани, название дизайна, поставщик, кратность рулона.
- `dim_workshop` — цех (Солях, Инна, Инна2, Банный, Химки, Терра, Зеленоград,
  Яхрома, Гав ЯМ, Светлана, ФБС …), тип (цех / перемещение).
- `dim_destination` — `wb`, `ozon`, `sklad`, `sklad_kvant`.
- `dim_account` — кабинеты (`skazka`, `milky_garden`, `timeless`) и бренды.

### 4.2 Факты со стороны маркетплейсов

Уже есть: `wb_orders`, `wb_sales`, `ozon_orders`, остатки WB/Ozon/Selsup,
`sync_runs`. Добавляем:

- `price_snapshots` — цена и скидка по артикулу и дню.
- `ad_stats_daily` — реклама WB: показы, клики, расход по артикулу и дню.
- `promo_events` — акции и новости (то, что сейчас в файлах «Новости»).
- `finance_daily` — финансовые показатели по артикулам (по мере необходимости).
- `stock_daily` (представление) — остатки по артикулу, дню и месту хранения
  (ФБО WB/Ozon, ФБС, Склад, Склад Квант) и флаг `out_of_stock`.
  **Дни без остатка — ключевой признак**: без него спрос на часто заканчивающихся
  товарах занижается, и модель учится неверно.

### 4.3 Производство и поставки

- `fabric_receipts` — приход ткани: дата, поставщик, ткань, метраж, цена, накладная,
  заявленный и фактический метраж, брак.
- `production_task` — задание цеху: номер задания, бренд, цех, неделя
  (ISO-дата начала недели), направление, плановая дата поставки, статус.
- `production_task_line` — строка задания: артикул, плановое и фактическое
  количество, метраж, дата отгрузки, дата приёмки, № приёмки.
- `production_task_status_log` — журнал смен статусов. Статус в таблице
  перезаписывается, журнал позволит позже посчитать, как долго задание
  находилось на каждом этапе.
- `logistics_daily` — рейсы и их стоимость (Иваново → цех, отгрузки на ВБ/Озон,
  ФБС, возвраты). Вторично, не в первом этапе.

Производные сроки (представление `lead_times`):
закупка ткани → пошив → приёмка → доставка, по цеху и направлению.
Вместо зашитых 28 дней это распределение фактических сроков.

### 4.4 Решения (для обучения и оценки)

- `baseline_recommendation` — ночной расчёт **текущей формулы аналитика**
  (раздел 5), один к одному: артикул, направление, потребность, квант, дата расчёта.
- `analyst_decision` — что в итоге ушло в задания (берётся из
  `production_task_line` по дате и артикулу), плюс отметка «подтверждено / скорректировано».
- `outcome` (представление) — что получилось за N дней после решения:
  продажи, остаток, были ли дни без остатка, затоваренность.

### 4.5 Признаки и прогнозы

- `features_daily` — одна строка на артикул, направление и день: скорости
  продаж (7/30 дней), дни без остатка, остатки по местам, цена, реклама,
  календарные признаки, производство в пути и срок до прихода.
- `forecasts` — прогноз, версия модели, дата, горизонт.
- `model_runs` — запуски обучения и метрики.

## 5. Baseline — формула аналитика

Переносим в код без изменений, чтобы любая модель сравнивалась с ней.
Описание по листу «планирование» (детали формул сверить с аналитиком):

1. Скорость продаж WB и Ozon за 7 дней, за 30 дней и за предыдущие 30 дней;
   30-дневная скорость делится на (30 − дни без остатка).
2. Максимальная скорость = `MAX(7д, 30д, MIN(30д × 2, пред.30д))`.
3. До прихода текущего заказа (срок по умолчанию 28 дней) продаётся часть
   остатка и производства в пути. Считается остаток на дату прихода.
4. Потребность = целевая оборачиваемость (30 дней) × скорость − (остаток + в производстве),
   отдельно для WB и Ozon, округление до кванта.
5. Потребность в ткани = потребность × м/изд − наличие ткани у поставщика;
   распределение по цехам.

Внутри системы это модуль `baseline`, на него ссылаются и метрики, и будущие модели.

## 8. Вопросы к аналитику (часть закрыта владельцем)

Закрыто:

- **Формат артикула** `PT5930/6-17-17/1`: `PT` — бренд (без префикса — бренд
  Timeless), `5930` — код дизайна, `6-17-17` — коды размеров (пододеяльник —
  простыня — наволочка, `0` = нет), последнее число — вариант (с рюшами / без,
  молния / кнопки / пуговицы). Разбор — `domain/article.py`. Префиксы кроме
  пустого сохраняются как `brand_code`, но **не** привязываются к кабинету:
  в данных есть `MT`, `PC`, `AM`, `PA`, `PF`, `KK` и др. (подбренды), а кабинет
  берётся из того, где артикул встречается. Около 4,8 тыс. артикулов имеют
  старые форматы (`112/1-100220`, `1620/1630/1629`, `PT5223/104-116/сарафан/карнавал`)
  и остаются `parsed = false`, пока не определён их смысл.
- **Формулы листа «планирование»** подтверждены (раздел 5).
- **Нумерация недель.** Проверено по «Плану поставок»: номер недели в
  заголовке листа совпадает с календарной (ISO) неделей; листы на стыке
  месяцев объединяют две недели (например, `17.08–30.08` = «неделя 35»).
  «Новая нумерация с 32 недели» относится к **номерам заданий** (`№39_00068`),
  а не к неделям. Ключом остаются даты.

Допущение, требующее проверки (этап 4):

- **«Квант».** Владелец считает, что это название склада («Склад Квант»).
  В таблице, кроме того, есть лист **«кратность кванта»**: по ключу размера
  (`/0-0-24/`) он даёт, сколько штук помещается в коробку, а формула
  «планирование» округляет потребность до этой кратности, и «потребность в
  квантах» — число таких коробок. Значит, в формулах «квант» — это упаковочная
  кратность, а «Склад Квант» — отдельная сущность. Оба смысла сохраняем
  раздельно: кратность — в справочнике (этап 3), склад — в `selsup_stocks`
  (`warehouse_id = 10020`).

Остаётся открытым:

1. Что означают старые форматы артикулов (`112/1-100220`, `PT5223/104-116/сарафан/карнавал`)?
2. Какие параметры формул ручные (целевая оборачиваемость 30 дней, срок 28 дней)?
3. Когда решение считается принятым: момент создания задания, отправка цеху?
4. Какие статусы заданий считать завершёнными: `выпущено`, `закрыт`?
5. Как учитывать «перемещение со склада» (строки с цехом `ФБС`): это не пошив,
   а перевозка между складом и площадкой. Нужны ли они в обучении «куда везти»?

Закрыто владельцем (01.10.2026): «Склад» — это общий склад FBS Selsup
(`warehouse_id = 10001`), «Склад Квант» — склад Kvant (`10020`). В
представлениях это места `selsup_fbs` и `selsup_kvant`.

## 9. Метрики и критерий успеха

Определить вместе с аналитиком до этапа 5. Предварительно:

- точность прогноза спроса (WAPE/MAE по артикулу и неделе) против baseline;
- доля дней без остатка (потерянные продажи);
- доля затоваренности (остаток сверх N дней оборачиваемости);
- совпадение рекомендации с решением аналитика (как вспомогательная метрика:
  совпадение не означает, что решение было верным).

Оценка — только на временной отложенной выборке, без перемешивания по времени.

## 11. Статус реализации (этапы 1–2, 30.09.2026)

Сделано и проверено на реальных данных Drive и на настоящем Postgres 16
(64 теста: разбор, оркестрация бэкфилла на фейках, HTTP-источники на
подменённом транспорте, интеграционные тесты SQL).

**Этап 1 — ежедневный сбор** (`sync`, добавлено к существующему):
цены WB и Ozon (снэпшот на день), реклама WB (последние 7 дней, апсертом),
движения Selsup — приёмки и отгрузки «Склада»/«Склада Квант»/FBS (последние
3 дня, ключ дедупликации `movement_key`). Остатки по местам, дни без остатка

артикулов — `dim_article` (`refresh-dims`).

**Этап 2 — бэкфилл** (`backfill`, читает Drive сервисным аккаунтом, только

Проверка: остатки по кабинетам сходятся с исходными файлами (Сказка 69 190
шт. на WB против 69 068 днём ранее и т. д.); справочник — 40 029 артикулов,
из них 7 257 в старых форматах (`parsed = false`).

**Что выяснилось по пути (и учтено в коде)**

- WB в отчёте остатков **не перечисляет товары без остатка**, поэтому «дни
  без остатка» нельзя считать по самому отчёту. Каталог на день берётся из
  снэпшота цен; артикул из каталога без остатка считается нулевым. На данных
  сентября у артикулов с заказами WB был без остатка в среднем 8–11% дней.
- В старых файлах остатков Selsup (06–19.08) нет колонки кабинета; кабинет
  восстанавливается по `skuId` из более новых файлов. Файл, из которого
  не распознано ни одной строки, больше не считается загруженным.
- Даты снэпшотов бэкфилла — дата изменения файла по Москве (так же, как «дата
  наблюдения» ночного синка).

**Ограничения и пробелы**

- **Живой API не проверен.** Цены, реклама и движения Selsup написаны по
  контрактам `reference/nightly_export.py` и проверены на разборе и
  пагинации, но не на настоящем API (на машине разработки нет ключей).
  Первый ночной прогон надо проверить командой `status`.
- **История остатков и цен WB/Ozon — только с 10–11.09.2026** (с начала
  архива); раньше в Drive этих данных нет. Заказы: WB с 02.07, Ozon с 12.07.
  Глубже — только через API (этап 2б, проверка лимитов WB/Ozon).
- **Дыра:** движения Selsup за 19.09.2026 отсутствуют (нет дневного файла).
  Ночной синк захватывает 3 дня и её не закроет; нужна разовая докачка по API.
- У 46% движений Selsup нет кабинета, у 6% — артикула: это SKU, которых уже
  нет в остатках, связать их не с чем.
- Каталог Ozon включает архивные карточки: перед чтением флагов `ozon_out`
  фильтровать артикулы по наличию заказов или остатков в истории.
- Второй лист выгрузки Ozon («остатки по складам FBO») в базу не попадает.
- Продажи Ozon отдельной таблицей не собираются (есть только заказы).
