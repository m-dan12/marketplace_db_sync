# reference/nightly_export.py — статус

Это реальный код действующего скрипта, который сейчас (на момент копирования)
работает на сервере компании (`C:\Users\Proftex1\MarketplaceGateway\scripts\nightly_export.py`,
задача планировщика `NightlyAnalyticsExport`, каждую ночь в 3:00) — тянет
остатки/заказы/продажи из WB, Ozon и SelSup API и кладёт их как xlsx-файлы
на Google Drive.

**Он здесь только как эталон реальных API-контрактов** (эндпоинты,
параметры запросов, поля ответов, пагинация, обработка ошибок WB/Ozon/SelSup) —
все ключевые детали уже выписаны текстом в [`../TASK.md`](../TASK.md), но
если что-то в ТЗ неполно или неточно, этот файл — источник истины по факту,
как оно реально работает в проде.

## Архитектурный статус: устаревший, НЕ образец для подражания

Этот скрипт написан **до** решения переходить на Clean Architecture для
новых проектов компании. У него сознательно другая, более простая (и для
целей нового проекта — недостаточная) организация:

- Один процедурный файл на 1000+ строк, без разделения на слои
  (данные/бизнes-логика/IO перемешаны в одних и тех же функциях).
- Результат — xlsx в памяти (`openpyxl.Workbook`), а не структурированные
  записи для БД.
- Нет портов/интерфейсов, нет DI, нет отдельного слоя для тестируемости —
  тестов нет вообще.
- Три отдельных запроса/файла на разные периоды (7д/30д/предыдущие 30д)
  вместо одного окна с фильтрацией на чтении (см. `TASK.md`, §5 — это
  прямо то, что в новом проекте нужно сделать иначе).

**Правило:** переиспользуй отсюда только факты о том, как устроены внешние
API (эндпоинты, параметры, форма ответа) — не копируй структуру кода,
организацию функций или подход "всё в одном файле". Новый код в этом
репозитории следует архитектуре, описанной в `TASK.md` (§2), независимо от
того, как устроен этот файл.

Не модифицируется и не запускается — держим только для справки.
